# adr

ADR(Architecture Decision Record, 설계 결정 기록)은 **"왜 이렇게 만들었나"** 를 남기는 문서다. PRD가 "무엇을"이라면 ADR은 "어떻게, 왜 그 길을"이다. 서술형·인터뷰에서 "왜 이렇게 했나요?"에 답할 근거가 된다.

## 언제 쓰나

- **쓴다**: 길이 둘 이상이었고 하나를 골랐다 · 시도했다가 버린 방법(숫자와 함께) · 임계값을 정했다 · 과제 문서가 비워 둔 것을 정했다
- **안 쓴다**: 버그 수정, 이름 바꾸기, 요구사항을 그대로 구현한 것(커밋과 테스트가 대신 말한다)
- **같은 결정의 작은 후속은 새 ADR 대신 앞 ADR에 더한다.** 결정 문단 끝에 "(HH:MM 더함)"을 붙인다.
- **앞 결정을 바꾸면 앞 ADR을 지금 결정으로 고친다.** "대체됨" 파일을 따로 만들지 않는다. 왜 바꿨는지는 맥락에 한 줄 적는다.
- **진행 계획("다음에 할 것")은 쓰지 않는다.** 계획은 금방 낡아서 결정과 엇갈린다. 계획은 `docs/HANDOFF.md`에 쓴다.

## 상태

- `채택`: 사람이 인터뷰나 대화에서 고른 것이다. `deciders`에 사람 이름을 쓴다.
- `제안`: AI가 혼자 정한 것이다. 쓴 직후 사람에게 "ADR-nnnn 확인 부탁"이라고 알린다. 사람이 확인해야 `채택`으로 바꾼다.

## 순서

1. `docs/adr/`가 없으면 만들고 아래 `README.md`(목록)를 만든다.
2. 같은 기능(`features`)을 가진 ADR이 이미 있으면 먼저 읽는다. 고칠지 새로 쓸지 정한다.
3. 번호는 이어서 매긴다. 지운 번호는 다시 쓰지 않는다.
4. 아래 틀로 쓴다. **제목 한 줄만 읽어도 결정을 알 수 있게** 쓴다.
5. `docs/adr/README.md` 목록 표에 한 줄 더한다.
6. 문체는 `docs/WRITING.md`를 따른다.

## 파일 틀 — `docs/adr/0003-orders-reject-duplicate-email.md`

```markdown
---
id: "ADR-0003"
title: "같은 이메일의 두 번째 가입은 409로 거절하고, 이메일은 소문자로 바꿔 비교한다"
status: "채택"          # 제안 · 채택
date: "2026-10-31"
deciders: ["정희록"]
features: ["F-01"]      # 관련 PRD 기능
criteria: ["F-01#AC2"]  # 이 결정이 답하는 수용 기준. 없으면 []
code: ["src/users/signup.ts"]     # 이 결정을 바꾸려면 열어 볼 파일
tests: ["src/users/signup.test.ts"]
related: []             # 같이 읽어야 하는 ADR
---

# ADR-0003 같은 이메일의 두 번째 가입은 409로 거절한다

## 맥락
무엇이 문제였나. 어떤 제약이 있었나. 실측한 숫자가 있으면 숫자로 쓴다.
(인터뷰에서 정했다면 "GRILL Q3"처럼 출처를 쓴다.)

## 결정
무엇을 하기로 했나. 한 문단.

## 고려한 다른 길
- 기존 계정에 덮어쓰기 — 다른 사람이 남의 계정을 가져갈 수 있어서 고르지 않았다

## 결과
이 결정으로 쉬워진 것과 어려워진 것. 되돌리려면 무엇을 고쳐야 하나.
```

## 목록 — `docs/adr/README.md`

```markdown
# 설계 결정 기록

| ADR | 제목 | 상태 |
|---|---|---|
| [0001](0001-....md) | ... | 채택 |
```

- 맥락에는 **왜**와 **숫자**를, 결과에는 **되돌리려면 무엇을 고치나**를 꼭 쓴다. 평가자가 가장 자주 묻는 두 가지다.
- `code`·`tests`·`criteria`는 본문에 적은 파일·기준과 같게 둔다. 파일을 옮기면 같이 고친다.
