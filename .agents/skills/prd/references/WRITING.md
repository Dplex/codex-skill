# 문서 문체와 용어

대화·ADR·PRD·HANDOFF·커밋 메시지의 문체 기준이다. 말투의 기본은 `AGENTS.md`의 ELI20이다. 이 문서는 문서별 차이와 자주 틀리는 표현을 다룬다.

| 쓰는 곳 | 문체 |
|---|---|
| 사람과의 대화 | ELI20. 친근하고 짧게, 결론부터 쓴다 |
| ADR·PRD·HANDOFF 본문 | "~한다" 평서형. 제목·표·목록은 "테스트 12개 통과"처럼 명사형으로 줄여도 된다 |
| 화면 문구(버튼·안내문) | 사용자가 할 일과 그 결과를 짧게 쓴다. 버튼은 동작("저장하기"), 안내문은 조건과 다음 행동("이름을 입력해 주세요") |
| 커밋 메시지 | 변경 내용이 드러나는 한 줄. "~한다"로 쓴다 |

## 원칙

1. **처음 한두 문장에 문제와 결과를 쓴다.** 소제목 하나에는 한 가지 내용만 담는다. 제목에서 한 말을 본문 첫 문장에서 반복하지 않는다.
2. **독자가 찾을 수 있는 이름으로 쓴다.** "아까 그 방식", "묶음 A"처럼 작업자만 아는 이름 대신 `F-03`, `ADR-0002`, 함수 이름을 쓴다.
3. **번호는 뜻과 함께 쓴다.** `D2`만 적지 말고 "D2(재시도 횟수 결정)"처럼 처음 한 번은 무엇인지 함께 적는다.
4. **현재 상태·완료한 일·할 일을 구분한다.** "지원한다", "F-02에서 구현했다", "다음 모듈에서 할 예정이다"처럼 시점을 밝힌다. "진행했다"와 "완료했다"도 구분한다.
5. **정의는 관계가 드러나게 쓴다.** "주문 = 장바구니"보다 "결제를 누르면 장바구니로 주문을 만든다"처럼 무엇이 언제 생기는지 쓴다.
6. **대상·상태를 직접 쓴다.** 값이 없는 것, 저장되지 않은 것, 화면에 안 보이는 것은 서로 다른 상태다. 한 단어로 뭉뚱그리지 않는다.
7. **판단에 필요한 예시는 실제 입력 하나로 든다.** 예: "수량 0인 주문은 400으로 거절하고, DB에는 남기지 않는다."
8. **제안과 결정을 구분한다.** ADR이 `제안`이면 "이렇게 정했다"가 아니라 "이렇게 하기를 제안한다"라고 쓴다.
9. **표현을 다듬으면서 사실을 바꾸지 않는다.** "구현하지 않았다"와 "테스트하지 않았다"는 다르다. 부드럽게 쓰려고 제약을 지우지 않는다.
10. **억지로 순화하지 않는다.** 버튼·드래그·API·캐시처럼 널리 쓰는 용어는 그대로 쓴다. 뜻을 다시 추측해야 하는 순화어는 피한다.

## 이렇게 바꾼다

금칙어 사전이 아니다. 뜻이 분명한 문장까지 기계적으로 바꾸지 않는다.

| 다듬기 전 | 권장 표현 | 이유 |
|---|---|---|
| 처리한다 | 서버가 중복 요청을 거절한다 | 누가 무엇을 하는지 드러낸다 |
| 잘 된다 · 문제없다 | 테스트 8개 통과(F-01 AC1~AC3) | 확인한 범위를 숫자로 쓴다 |
| 들어갔다 · 반영됐다 | F-02에서 구현했다 / 커밋 a1b2c3에 포함했다 | 어디에 어떻게 포함됐는지 쓴다 |
| 에러 난다 | `POST /orders`가 500을 반환한다(재고 0일 때) | 입력과 결과를 구체적으로 쓴다 |
| 일단 이렇게 | 이렇게 하기를 제안한다(ADR-0003 제안) | 확정 여부를 밝힌다 |
| 나중에 | 범위 밖이다(PRD 범위 밖 목록) / 다음 모듈에서 할 예정이다 | 하지 않을 것과 미룬 것을 구분한다 |
| 빠르다 · 느리다 | 1,000건 기준 0.8초 | 측정 조건과 값을 쓴다 |

조사는 앞말에 붙인다("API를", "PRD에서"). 한 문장을 쉼표와 괄호로 길게 잇기보다 내용별로 나눈다.
